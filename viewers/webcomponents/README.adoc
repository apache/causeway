The Causeway web-component modules provide framework-neutral browser components backed by the Causeway rich GraphQL schema.
The foundation module includes a GraphQL client provider, coordinated application menu bars, service-action prompts and invocation, coordinated object contexts, safe effective-grid and fallback composite objects, toolkit-qualified read-only scalar and ordinary-action presentation with native rollback, explicitly enabled property editing, normalized interaction results, lazy collections, and an optional cohesive theme.
It deliberately has no dependency on HTMX, React, Vue, Svelte, Wicket, Bootstrap, or a browser component-authoring framework.
The separate optional HTMX module adds canonical routing, a stable shell, history, custom-page selection, and fragment lifecycle above those components.

This page explains how to run the automated verification and how to exercise the components manually against a Causeway application.

== Prerequisites

The Maven build requires JDK 17 or later.
The dependency-free browser tests use the Node.js built-in test runner.
Manual end-to-end verification requires a Causeway application exposing the rich GraphQL schema.

== Automated verification

Run all commands from the repository root unless a command explicitly changes directory.

=== Web-component Maven lifecycle

Select a JDK 17 or later installation and run the complete module verification:

[source,shell]
----
export JAVA_HOME="$HOME/.sdkman/candidates/java/17.0.18-tem"
export PATH="$JAVA_HOME/bin:$PATH"

mvn -f viewers/webcomponents/pom.xml clean verify
----

A successful run reports the foundation and HTMX Node test totals and completes the foundation, HTMX, vanilla sample, and Petclinic sample modules:

[source,text]
----
tests 103
pass 103
fail 0

tests 4
pass 4
fail 0
BUILD SUCCESS
----

The exact test count can increase as further components are added.
A non-zero failed-test count or Maven `BUILD FAILURE` indicates that verification has not passed.

=== Direct browser-package tests

The browser package can be tested independently of Maven:

[source,shell]
----
cd viewers/webcomponents/foundation
node --test --test-concurrency=1
----

The tests cover targeted application and service discovery, bounded menu and grid parsing, coordinated menu generations, standalone and declarative bars, grouped service-action state, service prompts and results, deterministic and fallback object layout planning, context-owned structural resources, generated rich-schema naming, schema diagnostics, executor behavior, selection coordination, read-only presentation eligibility and fallback, ordinary action adaptation, property and object-action semantic commands, editor selection, validation, cancellation, mutation serialization, typed outcomes, partial errors, component lifecycle, context propagation, and integrated state distribution.

=== Related GraphQL modules

Run the GraphQL model and viewer tests to detect incompatibilities with the endpoint consumed by the components:

[source,shell]
----
mvn -f viewers/graphql/pom.xml -pl model,viewer test
----

=== BOM, source, and OpenSpec checks

Validate the dependency-management entry, source formatting, and active OpenSpec change:

[source,shell]
----
mvn -f bom/pom.xml validate

git diff --check

openspec validate add-generic-htmx-web-component-viewer --strict
----

The OpenSpec command should report:

[source,text]
----
Change 'add-generic-htmx-web-component-viewer' is valid
----

=== Packaged browser resources

After `mvn verify`, inspect the foundation artifact to confirm that the browser modules were packaged as servlet resources:

[source,shell]
----
jar tf viewers/webcomponents/foundation/target/causeway-viewer-webcomponents-foundation-*-SNAPSHOT.jar \
  | grep 'META-INF/resources/causeway-webcomponents/'
----

The listing should include `META-INF/resources/causeway-webcomponents/index.mjs`, its imported modules, the independently lazy `vaadin-reference`, `vaadin-fields`, and `vaadin-actions` assets, their policy metadata, and their distributable legal files.

== Manual browser verification

The preferred manual test serves the page and GraphQL endpoint from the same Causeway application origin.
This avoids cross-origin and authentication-cookie differences that can obscure component behavior.

The repository provides HTMX and Vue Petclinic applications over one shared deterministic JPA/H2 domain and rich GraphQL contract, plus `viewers/webcomponents/sample-html` as the stable low-level vanilla-component fixture.
The HTMX Petclinic application is the presentation reference for the Vue sample's application-owned shell and exact-type HomePage, PetOwner, Pet, and Visit pages.
Start either Petclinic viewer from the repository root with:

[source,shell]
----
./viewers/webcomponents/sample-htmx-petclinic/run.sh
./viewers/webcomponents/sample-vue-petclinic/run.sh
----

Run only one application at a time because both use port 8080 by default.
Open `http://localhost:8080/htmx` for HTMX or `http://localhost:8080/vue/` for Vue.
The HTMX application also exposes `/wicket/`; sign in as `sven` with password `pass` for comparison.
See link:sample-htmx-petclinic/README.adoc[`sample-htmx-petclinic/README.adoc`], link:sample-vue-petclinic/README.adoc[`sample-vue-petclinic/README.adoc`], link:htmx/README.adoc[`htmx/README.adoc`], and link:vue/README.adoc[`vue/README.adoc`] for routes, customization, and acceptance contracts.

The vanilla sample supplies its own deterministic JPA/H2 data, the same rich GraphQL endpoint, packaged foundation modules, and stable low-level automation hooks.
Start it from the repository root with:

[source,shell]
----
mvn -f viewers/webcomponents/pom.xml -Prun-sample-html
----

Then open `http://localhost:8080/sample-html/index.html` and wait for the application state to become `ready`.
See link:sample-html/README.adoc[`sample-html/README.adoc`] for port overrides, the packaged-jar alternative, and the automation contract.

=== Install the local artifact

When testing from a source checkout, install the web-component artifact into the local Maven repository:

[source,shell]
----
mvn -f viewers/webcomponents/pom.xml install
----

Add the foundation artifact to an application using components directly:

[source,xml]
----
<dependency>
    <groupId>org.apache.causeway.viewer</groupId>
    <artifactId>causeway-viewer-webcomponents-foundation</artifactId>
    <version>${causeway.version}</version>
</dependency>
----

Add `causeway-viewer-webcomponents-htmx` as well when the application requires the generic server router and shell.
The foundation artifact exposes its entry module and theme as standard `META-INF/resources` resources:

[source,text]
----
/causeway-webcomponents/index.mjs
/causeway-webcomponents/theme.css
----

=== Configure the GraphQL schema

The component defaults assume a combined schema whose rich API is beneath the `rich` query field.
A representative application configuration is:

[source,properties]
----
causeway.viewer.graphql.schema-style=SIMPLE_AND_RICH
causeway.viewer.graphql.resources.structural-metadata-response-type=DIRECT
spring.graphql.path=/graphql
----

`RICH_AND_SIMPLE` also places the rich API beneath its configured top-level field.
The default rich top-level field name is `rich`.
Direct structural metadata enables authorized effective-grid retrieval; if the policy remains `FORBIDDEN`, `<cw-object>` uses its canonical fallback without disclosing the resource body or authorization policy.

If the application uses `RICH_ONLY`, the generated object lookup fields are at the query root.
Set an empty `rich-root-field` attribute in that case:

[source,html]
----
<cw-graphql-client
    endpoint="/graphql"
    rich-root-field="">
</cw-graphql-client>
----

If the application customizes the rich top-level field or lookup grammar, configure the provider's `rich-root-field`, `lookup-argument-name`, `object-field-prefix`, and `object-field-suffix` attributes to match.
The Causeway defaults for lookup are argument name `object`, an empty field-name prefix, and an empty field-name suffix.

=== Create a same-origin test page

Serve a temporary page from the Causeway application with markup similar to the following:

[source,html]
----
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Causeway web-component verification</title>
  <script type="module" src="/causeway-webcomponents/index.mjs"></script>
</head>
<body>
  <cw-graphql-client endpoint="/graphql">
    <cw-menubars></cw-menubars>
  <cw-object-context
        logical-type="university.dept.Department"
        object-id="1">
      <cw-object editable></cw-object>
      <cw-interaction-controller></cw-interaction-controller>
    </cw-object-context>
  </cw-graphql-client>
</body>
</html>
----

Replace the example logical type and object identifier with values present in the application under test.
The logical type is the Causeway logical type name, not the generated GraphQL type name.
The object identifier is the identifier accepted by the rich GraphQL lookup input.

A source-tree version of this page is available at `viewers/webcomponents/foundation/demo/index.html`.
That page imports the unbundled modules directly and expects a same-origin `/graphql` endpoint.

=== Standalone static serving

For module-loading checks, the source-tree demonstrator can be served directly:

[source,shell]
----
cd viewers/webcomponents/foundation
python3 -m http.server 8081
----

Open `http://localhost:8081/demo/`.
This arrangement does not itself provide `/graphql`.
To use a GraphQL service on another origin, set an absolute endpoint and configure CORS and authentication appropriately, or inject a custom executor that uses the application's networking policy.
For realistic authentication behavior, same-origin serving is usually simpler.

== Manual inspection checklist

=== Rendered content

Verify that `<cw-menubars>` reaches `data-menu-state="ready"` or bounded `partial-error`, renders labelled effective primary, secondary, and tertiary navigation without hidden entries, and preserves visible disabled actions with reasons.
Verify that `<cw-object>` reaches `data-layout-state="ready"` for an authorized effective grid or `fallback` when the resource is unavailable.
Verify that its generated `<cw-object-header>` renders object title and identity and each discovered member is placed at most once.
Verify that each visible property has one Causeway label and an `<output>` value, with eligible standard values using genuine read-only internal fields under the default toolkit and established renderers under explicit native rollback.
Verify that ordinary action controls use internal Vaadin Buttons and each qualified application-menu tier uses an internal Vaadin Menu Bar by default, while explicit native rollback restores established buttons and menus and prompt, property-interaction, and non-menu shell controls remain native.
Verify that values containing markup-like characters are escaped rather than interpreted as HTML.
Verify that hidden properties produce no visible content.
Verify that disabled properties expose `aria-disabled="true"` and their disabled reason.
Verify that component errors are rendered with `role="alert"`.

=== Initial network activity

Open the browser developer tools and inspect the GraphQL POST requests.
The initial load should perform a small series of operations named `CausewayDescribeTypes` using targeted `__type` introspection.
It should not download and inspect the complete GraphQL schema.

Application menus first perform targeted operation-root, application-entry, and referenced service-type introspection, one `CausewayReadApplicationEntry`, one same-origin no-store effective-menu GET, and grouped `CausewayReadServiceActionStates` operations by logical service type.
A composite shares those operations across its bars, while each standalone bar intentionally owns a separate generation.
After object schema discovery, one operation named `CausewayReadObject` should contain the combined active selection for the object header and all properties mounted during the initial rendering turn.
For the composite example, the first object operation includes `_meta.grid`; generated children then contribute member requirements to a coordinated delta operation.
Auto layout also performs one same-origin no-store GET for the opaque grid reference, while forced fallback performs no structural-resource request.
There should not be one object operation per component.

=== Context and component state events

Register listeners in the browser console:

[source,javascript]
----
document.addEventListener(
  'causeway-object-context-state-change',
  event => console.log('context', event.detail.state)
);

document.addEventListener(
  'causeway-component-state-change',
  event => console.log('component', event.detail.state)
);
----

Refresh the active object projection from the browser console:

[source,javascript]
----
document
  .querySelector('cw-object-context')
  .context
  .refresh();
----

The context should move through `object-loading` and then `ready` or `partial-error`.
A transport or schema failure with no usable object data should produce `terminal-error`.

=== Schema-cache reuse

After the first context becomes ready, create another context for an object of the same logical type:

[source,javascript]
----
const provider = document.querySelector('cw-graphql-client');
const original = document.querySelector('cw-object-context');
const second = original.cloneNode(true);

second.setAttribute('object-id', '2');
provider.append(second);
----

The second context should execute its own object read while reusing the first context's schema description.
The network log should therefore show one additional `CausewayReadObject` operation but no repeated introspection for that generated object type.
The two context elements should retain independent object state.

=== Delta loading

To observe projection growth clearly, start with a page containing the header and only the `name` property.
After it becomes ready, mount another property:

[source,javascript]
----
const context = document.querySelector('cw-object-context');
const property = document.createElement('cw-property');

property.setAttribute('id', 'code');
context.append(property);
----

The context should issue one delta object operation containing the newly required `code` selection rather than refetching `name` and `_meta`.
A later explicit `refresh()` should execute the complete currently active projection.

=== Partial errors

Use an object or authorization scenario in which one member fails while another succeeds.
The successful member should retain and render its data.
The failing member should receive the member-relative GraphQL error and render its error state.
The enclosing object context should report `partial-error` rather than discarding the successful snapshot.

== Troubleshooting

=== Maven rejects the Java version

The repository enforcer requires JDK 17 or later.
If Maven reports an older detected JDK, update both `JAVA_HOME` and the leading entry in `PATH` before rerunning the build.

=== Generated object type is not found

Confirm that `logical-type` contains the exact Causeway logical type name.
Do not supply a generated name beginning with `rich__`.
Confirm that the application's GraphQL API scope includes the domain type.

=== GraphQL validation reports an unknown lookup field

Confirm whether the application uses a combined schema or `RICH_ONLY`.
Confirm the configured rich top-level field and lookup argument, prefix, and suffix settings.
Adjust the `<cw-graphql-client>` attributes to match those settings.

=== Requests are rejected or redirected

Prefer a page served from the same application origin as `/graphql`.
For a cross-origin page, configure CORS explicitly and inject an executor if credentials, CSRF handling, or application-specific headers are required.

=== Application menus are unavailable

Confirm that the rich GraphQL root exposes `application.menuBars` and that structural metadata response type is `DIRECT` or `ATTACHMENT` rather than `FORBIDDEN`.
Inspect `causeway-menubars-state-change` and bounded `causeway-menubars-diagnostic` events without logging the effective XML response body.

=== Effective grid is unavailable

Confirm the structural metadata response policy and inspect the grid GET status without logging its response body.
A forbidden, missing, malformed, or unsafe resource should produce a bounded layout diagnostic and canonical fallback rather than an empty object.

=== The page remains empty

Inspect `causeway-object-context-state-change` and `causeway-object-layout-state-change` events and the GraphQL response body.
Check for `terminal-error`, an unsupported member, a hidden member, or a missing object.
Verify that `/causeway-webcomponents/index.mjs` and all imported `.mjs` resources return JavaScript rather than an HTML error page.
