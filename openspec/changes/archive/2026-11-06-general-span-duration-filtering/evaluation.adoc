== Architecture comparison

|===
|Location |Visibility / completion |Ownership / operational cost |Savings boundary |Assessment

|JVM SpanProcessor/exporter |Sees only that process's spans; onEnd does not close async/remote descendants |Would require separately integrated Boot and agent hooks; must not add a second SDK |Potential application export savings if buffering were safe |Reject unrestricted local pruning: cannot prove distributed ancestor closure
|Collector trace buffer |Can group received spans by trace ID, but routing/late/missing spans remain assumptions |Stateful deployment, trace-affine routing, bounded buffering and decision caches |Potential Collector-to-backend savings, not application-to-Collector savings |Prototype replay boundary; completion remains a feasibility gate
|Backend/UI |Can inspect stored graph; incomplete ingestion and backend-specific queries still matter |Backend-dependent; no SDK ownership change |Display noise; storage already paid unless a separate storage transformation exists |Viable separately scoped alternative, not export filtering
|Whole-trace tail sampling |Keeps/drops a trace decision, not individual trivial spans |Existing Collector component with state/cache/routing requirements |Downstream trace volume |Control only; not a replacement answer to the individual-span question
|===

Pinned Collector source reference: https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.164.1/processor/tailsamplingprocessor/README.md[contrib v0.164.1 tail-sampling README], latest release at the lookup date (published 2026-10-26).
It states that all spans for a trace must reach the same Collector and that late spans may inherit cached decisions without influencing the original decision; after cache removal they may be reconsidered as a new trace fragment.
Its decision wait and trace limits are operational bounds, not proof of distributed completeness.
The Collector binary is not installed or deployed by this investigation.

API sources checked before prototype work include protobuf generated-message serialization and the resolved Micrometer 1.8.0-RC1 Tracer/Span/TraceContext builder signatures.

== Experiment contract

The candidate is a standard-library replay buffer, not a production processor or Collector plugin.
Only a trusted closed-fixture manifest permits pruning; timeout/pressure/unknown data retains input and switches the replay session to conservative pass-through.
A deliberately unsafe wait-window mode is a negative control used to demonstrate the late-descendant failure, never a supported setting.
Default replay bounds are eight pending traces, 256 pending spans, 1 MiB of serialized pending model data, decision age 100 replay-clock units, eight cached decisions and cache lifetime 100 units.
The declared larger corpus preset is 128 traces, 4,096 spans, 16 MiB and 128 cached decisions, retaining the same age/lifetime settings.
These bound queued model data and identity-cache counts, not total process RSS or the caller's already-materialized input.
Declared benchmarks use three warmups and ten measured repetitions over small (32 spans), deep (1,024), deep-with-error (1,024) and concurrent (64 traces × 32 spans) datasets at an experimental 10 ms threshold.
No value is a supported production default.

== Safety counterexamples and failure handling

[cols="<,>,<"]
|===
|Experiment |New orphaned retained edges |Meaning

|Retain on timeout |0 |Pending input and later arrivals pass through; no unsafe pruning decision
|Prune after wait window |1 |Useful late child references a parent already removed
|Unexpected child after declared fixture close |1 |Detecting the late arrival does not recover the pruned parent
|Late child after decision-cache expiry |1 |Forgetting a decision does not make a trace fragment complete
|===

Decision-cache eviction is bounded in the tests (two retained records after ten closes), but is not a late-span safety guarantee.
Overflow, byte/span/trace pressure, mismatched manifests and shutdown release pending input and latch conservative pass-through.
Modelled exporter/backpressure failures are counted separately as delivery failures, not intentional pruning; there is no unbounded retry queue.
These are synchronous deterministic sink-failure experiments, not live network/exporter interruption tests.

Whole-fast-trace sampling and UI projection controls were labelled models: sampling drops both spans of a complete trivial trace; the UI projection shows one while storing/exporting both.
Neither is reported as a deployable individual-span filtering integration.

== Decision and production follow-up boundary

*No-go for unrestricted live duration pruning with the existing arbitrary async/remote-span contracts.*
The counterexamples disprove the wait-window/finite-cache safety claims of the evaluated strategy; an ended parent and bounded wait do not prove that future useful descendants cannot reference it.
The conservative bounded alternative preserves safety by retaining uncertain data, but therefore provides no guaranteed general pruning benefit.

*Conditional feasibility: explicitly closed offline datasets only.*
The oracle demonstrates potential topology-preserving pruning and stage-specific size reduction when an external test driver supplies the complete captured set.
Observed manifests and finished fixture processes are not deployable distributed completion signals, so this conditional result does not authorize a live JVM/Collector filter.

A production follow-up would need an approved concrete closure or genuinely child-free eligibility contract, trace-affine visibility/routing, documented late/missing-span behavior, bounded byte/state/backpressure handling and tests against actual pipeline/export failures.
It must preserve single-owner Boot/agent integration and separately update observation-policy requirements and operator guidance before enabling any threshold.
Alternatively, pursue backend/UI collapsing or whole-trace sampling as a separately stated goal, without claiming equivalent individual-span export/storage savings.
No new application configuration, profile, SDK/exporter, dependency or production default was introduced here.
