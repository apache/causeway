## Context

The shared PDF reader places its controls above an independently scrollable page viewport, but previous-page and next-page currently call `scrollIntoView()` on a page placeholder.
A browser can scroll every eligible ancestor for that operation, so a wide Petclinic page may move the outer document as well as the reader viewport and leave the toolbar above the visible window.

The resource link is currently below the viewport after a visible canvas-accessibility sentence.
The zoom controls expose only a changing text label between decrement and increment buttons, so a user who leaves page-width fitting cannot select that mode again.
The sample document contains reader-oriented test phrases rather than domain content, and the automatic reader is rendered in a full-width card below the PetOwner two-column layout.
The original Apache Causeway Petclinic modeled an owner attachment as a PDF and placed it in the secondary column, which provides the domain precedent for a clinic-agreement fixture.

The foundation remains responsible for PDF reader behavior.
HTMX and Vue remain thin, equivalent hosts, while the existing GraphQL resource controller remains authoritative for the Blob URL and response.

## Goals / Non-Goals

**Goals:**

- Keep page-control navigation within the PDF viewport and keep the surrounding page and toolbar stable.
- Put the persistent authorized resource link in available toolbar space.
- Make page width, page height, page fit, and bounded percentage zoom choices directly selectable while retaining incremental controls.
- Remove the visible canvas disclaimer while retaining accurate, bounded accessibility semantics.
- Replace reader-demo content with a deterministic, realistic multipage pet-owner clinic agreement.
- Place the automatic agreement in the PetOwner secondary column in equivalent HTMX and Vue pages.
- Hide the redundant property label and let the reader consume the full Agreement card width.
- Verify behavior at wide and narrow viewports under the supported host and presentation policies.

**Non-Goals:**

- Changing PDF.js, Blob qualification, GraphQL resource authorization, content disposition, safety limits, renderer precedence, or lifecycle ownership.
- Adding PDF text, annotation, form, signature, print, search, outline, thumbnail, attachment, XFA, or script layers.
- Making the sample agreement editable, uploadable, legally effective, or generated by an application-specific PDF library.
- Adding a new public PDF element or new PDF presentation attributes.

## Decisions

### Scroll the owned viewport directly

Previous-page and next-page navigation will calculate the target page's position within `[data-causeway-pdf-viewport]` and scroll that element directly.
It will not call `scrollIntoView()` on the page placeholder because that API can also reposition the host document.
Focus will remain on the activated toolbar control while it remains enabled; navigation to a boundary will move focus to the available opposite page control rather than leave focus on a disabled control.
The outer document scroll position will remain unchanged within a small rendering tolerance, and the existing observer will continue to establish current-page state.

An alternative was to make the toolbar sticky while retaining document-level scrolling.
That would mask only part of the problem, could overlap host content, and would still mutate an ancestor the reader does not own.

### Make zoom mode directly selectable

The read-only zoom status will become an accessible native selector between the existing zoom-out and zoom-in buttons.
It will offer `Page width`, `Page height`, `Page fit`, the existing `Actual size` mode, and the standard `50%`, `75%`, `100%`, `125%`, `150%`, `175%`, and `200%` choices.
Selecting a fit mode will update the reader's zoom state, rerender pages through the existing bounded rendering pipeline, preserve the current page, and permit later restoration of that mode after incremental zooming.
The existing buttons will remain available with their established 25-to-400-percent bounds; when used from a fit mode they will continue from 100 percent and the selector will reflect the resulting percentage, including a non-standard percentage when necessary.
Page-height scale will be derived from the owned viewport's available block size and the PDF page height, without inspecting or moving a host scrolling ancestor.

An alternative was to add a reset button dedicated to page width.
That would solve only one restoration path and would not expose the reader's other existing fit mode or the requested page-height mode.

### Put the resource link in the reader toolbar

The existing `lobMarkup` output will be composed inside the reader toolbar after the page and zoom controls, with a styling hook that can consume remaining inline space.
The link will remain the same authorized URL and Blob metadata presentation and will remain present in manual, loading, ready, failed, password-rejected, and safety-limit states.
Link-only mode will continue to use ordinary Blob markup without mounting a reader toolbar.

An alternative was to duplicate the link at the top and bottom.
That would create redundant focus targets and make the resource action less predictable.

### Remove only the visible disclaimer

The standalone visible sentence about canvas images will be removed from reader markup and styling.
Page placeholders, canvases, the reader region, status, controls, and resource link will retain concise accessible names, and no markup will claim that rendered pixels expose PDF text.

An alternative was to visually hide the same sentence.
That would preserve unnecessary verbosity for assistive-technology users without adding a meaningful alternative to the document.

### Generate an owner-specific clinic agreement deterministically

`PetClinicPdfDocument` will generate a stable multipage clinic agreement using fixed legal-style sections, the authoritative sample owner identity, relevant pet names, and deterministic filenames and bytes.
It will not use the current clock, random values, external resources, runtime PDF services, or a new dependency.
The automatic, manual, and link-only demonstrations will refer to agreement content through their existing owning object relationships so all modes remain covered with realistic data.

An alternative was to copy binary PDF files from the historical Petclinic repository.
Code generation keeps fixture provenance, content, determinism, and reviewability local while allowing the current sample identities to appear in the document.

### Place the automatic agreement in the secondary PetOwner column

The HTMX and Vue PetOwner pages will move the Agreement card inside `petclinic-object-collections`, after the existing Pets and Visits cards, matching the historical secondary-column relationship.
The card will provide the visible Agreement heading.
The property will declare `LabelPosition.NONE` in domain presentation metadata and `label-position="NONE"` in explicit host markup so generated and custom presentations agree and the reader is not indented by a label column.
Existing responsive CSS will stack the two columns at the established breakpoint; any agreement-specific rule will only constrain sizing and will not create a host-specific reader.

An alternative was to add a third page column.
That would reduce useful reader width, diverge from the established Petclinic composition, and complicate narrow-layout ordering.

## Risks / Trade-offs

- [Browser geometry and fractional layout can produce small outer-scroll differences] → Acceptance tests compare the outer scroll position with a bounded tolerance and assert toolbar visibility after repeated navigation.
- [A toolbar containing the zoom selector and long filename can crowd controls] → Keep selector labels concise, give the link a flexible wrapping slot, and test wide and narrow layouts without horizontal page overflow.
- [Page-height fitting can be confused with page-fit behavior] → Expose both choices explicitly and calculate page height from only the available viewport block size while page fit remains bounded by both dimensions.
- [Owner-specific PDF generation can become nondeterministic] → Use fixed content ordering, stable formatting, fixed document metadata, and byte-level repeatability tests.
- [Removing visible explanatory text reduces discoverability of canvas limitations] → Preserve concise programmatic page labels and the prominent authorized download link for external document handling.
- [Moving the card changes PetOwner heading and layout expectations] → Update HTMX/Vue parity assertions and screenshots around the explicit Agreement section and responsive order.
