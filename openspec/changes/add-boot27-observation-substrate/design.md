## Context

The archived `verify-boot27-micrometer-tracing` change proved that a Spring Boot 2.7.18 application can retain Micrometer Core 1.9.17 while using Micrometer Observation 1.10.13, Micrometer Tracing 1.0.12, the Micrometer OpenTelemetry bridge 1.0.12, and OpenTelemetry API 1.19.0.
It also proved that a Micrometer observation built from `GlobalOpenTelemetry` can parent a JDBC span generated by OpenTelemetry Java agent 1.31.0.
The proof currently lives in an isolated regression-test module and does not provide production beans or framework lifecycle utilities.

Causeway 4 places its observation integration in core configuration and uses an `observation` Spring profile to make telemetry opt-in.
The maintenance branch should preserve that architectural direction while adapting it to Java 11 and Spring Boot 2.7, which does not auto-configure Micrometer Observation or Tracing.

This phase establishes infrastructure only.
The following phase will use it from `InteractionServiceDefault` and `MemberExecutorServiceDefault`.

## Goals / Non-Goals

**Goals:**

- Add the compatibility-tested dependency set without changing Boot-managed Micrometer Core 1.9.17.
- Make a stable Causeway observation integration bean available to later framework modules.
- Make observation inactive and effectively free by default through `ObservationRegistry.NOOP`.
- Activate a real `ObservationRegistry` through the `observation` Spring profile.
- Connect the active registry to an `OtelTracer` built from the Java agent's `GlobalOpenTelemetry` context.
- Provide Java 11-compatible lifecycle support that reliably starts, scopes, records errors, stops, and clears an observation.
- Verify inactive, active-with-agent, active-without-agent, successful, and failing lifecycle paths.

**Non-Goals:**

- Instrument Causeway interactions, actions, property edits, Wicket requests, transactions, execution publishing, or persistence operations.
- Add an application-facing observability API to applib.
- Create an `OpenTelemetrySdk`, configure an application-owned exporter, or package the Java agent with production artifacts.
- Add sampling, baggage, dynamic runtime switching, duration filtering, or semantic tag policies.
- Upgrade the globally managed Micrometer version or Spring Boot version.

## Decisions

### Put the substrate in core configuration

The production integration will live under a dedicated observation package in `core/config`, and `CausewayModuleCoreConfig` will import its configuration.
The package will contain the registry integration, profile-specific configuration, and lifecycle helper needed by later core modules.

This matches the Causeway 4 direction, avoids introducing a new extension module for infrastructure that later core runtime services must consume, and keeps the Boot 2.7-specific wiring in one boundary.

**Alternative considered:** create an optional tracing extension containing all Micrometer dependencies.
This would reduce transitive dependencies for applications that never enable tracing, but core services would still need either an additional internal abstraction or a dependency on the extension.
That inversion adds more maintenance-branch code and diverges from the forward architecture, so it is rejected for this targeted backport.

### Manage validated versions centrally without overriding Micrometer Core

The BOM will define explicit properties and dependency-management entries for Micrometer Observation 1.10.13, Micrometer Tracing and bridge 1.0.12, and OpenTelemetry API 1.19.0.
It will not override `micrometer.version`.
`core/config` will declare the production dependencies it compiles against.

The bridge's transitive `opentelemetry-sdk`, `opentelemetry-sdk-common`, and `opentelemetry-sdk-trace` artifacts will be excluded at the production dependency declaration.
The OpenTelemetry Java agent and OTLP protobuf test collector remain test-only in the regression-test module.

**Alternative considered:** import a newer Micrometer BOM or set `micrometer.version` to 1.10.13.
This is rejected because it would replace the Micrometer Core version tested and managed by Spring Boot 2.7.18.

### Always expose one Causeway integration bean

Framework consumers will inject a Causeway-owned integration object rather than directly making `ObservationRegistry` optional at every call site.
The substrate will own a qualified Causeway registry so an unrelated application-defined `ObservationRegistry` cannot accidentally enable or disable framework observations.
The integration object will hold that registry, fall back defensively to `ObservationRegistry.NOOP`, report whether it is no-op, and create unstarted observations or observation providers with consistent Causeway naming support.

This keeps optionality at configuration time, makes profile behavior deterministic, and gives Phase 3 a simple dependency that behaves safely in every application.
The integration class is framework infrastructure and does not become a public applib service.

### Use profile-specific registry configuration

When the `observation` profile is inactive, configuration will supply `ObservationRegistry.NOOP` and will not construct tracer or bridge beans.
When the profile is active, configuration will create an `ObservationRegistry`, construct `OtelCurrentTraceContext`, `OtelBaggageManager`, and `OtelTracer` from `GlobalOpenTelemetry.getTracer(...)`, and register `DefaultTracingObservationHandler` with the registry.

The active configuration will not test for a private Java-agent implementation class.
When the agent is absent, `GlobalOpenTelemetry` supplies its no-op implementation, allowing startup and observation lifecycles to complete without export.

**Alternative considered:** fail startup when the profile is active but the Java agent is absent.
This is rejected because safe degradation is operationally preferable and was part of the validated compatibility behavior.

### Keep SDK and exporter ownership with the Java agent

Production code will never invoke `OpenTelemetrySdk.builder()` and will not configure OTLP exporters.
The only OpenTelemetry object obtained by the substrate is an API tracer from `GlobalOpenTelemetry`.
Deployment configuration remains responsible for attaching the Java agent and configuring service identity, sampling, endpoint, and exporter behavior.

This prevents disconnected trace contexts and duplicate export pipelines.

### Add an explicit observation lifecycle helper

A Java 11-compatible helper will own an observation and its opened scope across different framework callbacks.
It will start and open scope once, close scope before stopping, record any `Throwable`, and make cleanup idempotent enough for defensive framework shutdown paths.
After close, the registry must not retain the closed observation as current.

The helper belongs with the core observation substrate rather than in commons so that commons does not acquire Micrometer dependencies.

**Alternative considered:** defer lifecycle support until semantic spans are introduced.
This is rejected because lifecycle correctness is a foundational concern and is cheaper to test independently before interaction and action callbacks depend on it.

### Reuse the compatibility harness for the production exit gate

Focused unit tests will validate profile selection and lifecycle behavior with recording handlers.
The existing `regressiontests/tracing-compatibility` child process will depend on the production core-config integration and use it to emit the framework-owned test observation.
Its real-agent OTLP assertion will continue to prove that the production substrate joins the agent context and exports successfully.

This avoids creating a second agent harness and turns the Phase 1 proof into a regression guard for the production integration.

## Risks / Trade-offs

- **[Risk] Adding bridge dependencies to core configuration increases every application's runtime classpath even when observation is inactive.** → Keep initialization profile-gated, exclude SDK artifacts, and accept the small classpath cost in preference to a new maintenance-only abstraction layer.
- **[Risk] Applications may define their own `ObservationRegistry` bean.** → Qualify the Causeway-owned registry and inject it explicitly so application registries do not alter the profile contract.
- **[Risk] An active profile without an agent silently exports nothing.** → Treat this as intentional safe degradation and document agent attachment as an operational prerequisite for export.
- **[Risk] Scope leakage could corrupt parentage across requests on reused threads.** → Centralize lifecycle ownership, close scope in `finally`, clear retained references, and test success and failure cleanup.
- **[Risk] Bridge APIs are version-sensitive.** → Pin the exact compatibility-tested versions and isolate version-specific construction inside core configuration.
- **[Trade-off] This phase adds infrastructure without user-visible semantic spans.** → Keep the change independently testable and use it as the prerequisite for the narrowly scoped interaction/action instrumentation phase.

## Migration Plan

1. Add validated dependency-management entries while retaining Boot-managed Micrometer Core 1.9.17.
2. Add the core-config observation package, Java module declarations, and module import.
3. Add inactive and active profile tests plus lifecycle tests.
4. Update the compatibility harness to exercise the production integration under the real Java agent and without it.
5. Run dependency convergence, focused tests, and representative core startup tests.
6. Document the internal integration contract and operational requirement to attach the Java agent when export is desired.

Rollback removes the core-config observation package, its module import and dependencies, and the associated tests.
Because no semantic instrumentation or public API is introduced, rollback does not require application or data migration.
