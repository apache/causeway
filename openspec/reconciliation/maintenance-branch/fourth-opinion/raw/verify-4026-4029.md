# Fourth-opinion reconciliation audit — CAUSEWAY-4026 / CAUSEWAY-4029

Clean-room, adversarial. SOURCE = maintenance-branch (`ecp`), TARGET = `main`.
Forward-ports landed in main under different ticket numbers; searched by symbol/behaviour.

## Timeline context (decisive for interpretation)

The CAUSEWAY-4026/4029 commits under review modified an **early `CommandExportManager` model**
(`CommandExportManager.java`, `CommandExportKnownTargetValidator.java`, `ReplayableCommand.getExportable()`,
`CommandExportManager_moveCommandsUp/Down`, `makeSelectedExportable`).

On the **maintenance-branch HEAD** that whole `CommandExportManager` model was subsequently **replaced /
consolidated** (later tickets CAUSEWAY-4039/4042 etc.) into a unified **`CommandManager`** model:
- `CommandManager` implements `ReplayableCommandParticipantTracker`; exposes `isKnownParticipants`.
- `CommandKnownParticipantsValidator` (renamed from `CommandExportKnownTargetValidator`).
- `CommandManager_excludeCommands` / `_unexcludeCommands` / `_moveCommands` / `_exportSequence`.
- `CommandExportManager`, `ReplayableCommand_makeExportable`, `makeSelectedExportable`,
  `CommandExportKnownTargetValidator` are **all DELETED** on maint HEAD.

Evidence (maint HEAD `dom/replay/` listing has NO `CommandExportManager` / `makeExportable` /
`makeSelectedExportable` / `CommandExportKnownTargetValidator`; module registers only `CommandManager*`).

**main** has forward-ported the `CommandManager` model (matching maint HEAD behaviourally) **but ALSO still
retains the legacy `CommandExportManager` + `ReplayableCommand_makeExportable` + `makeSelectedExportable`**,
still registered in `CausewayModuleExtCommandLogApplib`. So main is a *superset* — it has the new model AND
carries the old one that maint HEAD deleted.

Consequently the correct comparison for strands 1-6 is **maint-HEAD `CommandManager` model vs main
`CommandManager` model** (both are the descendants of the 4026/4029 behaviour), not the deleted
`CommandExportManager`.

## Strand 1 — Per-command exportability  →  PRESENT (behaviourally equivalent)

The v2 4026 predicate `ReplayableCommand.getExportable()` → `CommandExportManager.isExportable()` became
`ReplayableCommand.isKnownParticipants()` → `CommandManager.isKnownParticipants()` in BOTH maint HEAD and main.

main `ReplayableCommand.java:257-264`:
```java
public boolean isKnownParticipants() {
    if (participantTracker == null) return false;
    return commandLogEntry().map(participantTracker::isKnownParticipants).orElse(false);
}
```
main `CommandManager.java:157-169`: iterates `commandLogEntries()`, accumulates each entry's `getResult()`
into a `knownParticipants` set until it reaches the target command, then returns
`validator().validateParticipants(entry, knownParticipants).isEmpty()`.

maint HEAD `CommandManager.isKnownParticipants` uses `validateParticipants(cle, knownParticipantsAsOf(id))`
where `knownParticipantsAsOf` accumulates prior results up to (excluding) the target. **Same semantics**:
a command is "exportable/known" iff every target + reference-parameter participant is either an export root
(domain service or reference data) or a result recorded by an earlier command in the baseline-bounded sequence.

Export-root predicate equivalent: main `ReplayContext.isExportRoot` (`ReplayContext.java:105-108`) =
`isDomainService(bookmark) || CommandReplayReferenceDataService.isReferenceData(...)`; maint HEAD identical.

Verdict: **PRESENT — equivalent.** Implementation differs cosmetically (accumulate-inline vs
`knownParticipantsAsOf` helper) but behaviour is the same. The v2 4026 tests (`exportable_is_true/false...`,
result-ordering, recording-disabled) are all covered by main's `CommandManager` semantics.

`if (!isActionCommand(...)) return empty;` → `if (entry.getCommandDto() == null) return empty;`.
980a4fb3e86 changed the message wording.

main `CommandKnownParticipantsValidator.java:70-84`: `validateParticipants` guards only on
`entry == null` (NOT on action-vs-property) — so property-edit targets ARE validated. Confirmed equivalent
to the v2 5889 change. maint HEAD identical.

Message text — main `CommandKnownParticipantsValidator.Failure.message()` (`:169-177`):
```
"%s, parameter %s: '%s' is unknown for command export; select a prior navigation or finder action that makes it known."
"%s, target '%s': is unknown for command export; select a prior navigation or finder action that makes it known."
```
maint HEAD `CommandKnownParticipantsValidator` produces the **identical** strings (verified by diff — only
formatting differs).

Note: the v2 980a4fb3e86 diff (against the *old* `CommandExportKnownTargetValidator`) shows a shorter
`"...is unknown."` form, but that was an intermediate state; the consolidated `CommandKnownParticipantsValidator`
on BOTH maint HEAD and main carries the fuller `"...is unknown for command export; select a prior..."` wording.
So main matches the authoritative (maint HEAD) source.

Verdict: **PRESENT — equivalent.**

required; move-after-target present in both. Not a gap.

## Strand 5 — Autoselect exportable commands for export  →  PRESENT (as automatic filter)

2932b6ae142 added `CommandExportManager_exportSelected.defaultSelected()` selecting `getExportable()==TRUE`.
In the consolidated model this became an **automatic filter** at export time rather than a UI default:

main `CommandManager_exportSequence.exportableCommands()` (`:101-105`):
```java
return commandManager.getCommandsInSequence().stream()
        .filter(ReplayableCommand::isKnownParticipants).toList();
```
`act` exports exactly `exportableCommands()`; `disableAct` disables when none. maint HEAD identical.

So exportable commands are auto-selected (only known-participant commands are exported); no manual selection
step at all. Also, main's `CommandManager_excludeCommands.defaultSelected()` auto-selects the *complement*
(`!isKnownParticipants`) for exclusion.

Verdict: **PRESENT — behaviour preserved** (auto-filter of exportable/known-participant commands).

## Strand 6 — Removal of 'make selected exportable' action  →  NOT APPLIED in main; behaviourally dead legacy

ea438afc7ee removed `CommandExportManager_makeSelectedExportable` (and on maint HEAD the whole
`CommandExportManager` + `ReplayableCommand_makeExportable` are gone).

main **still contains and registers**:
- `CommandExportManager.java` (legacy record model) — module import line 49, actions registered lines 110-124
  (`exportSelected`, `makeSelectedExportable`, `openCommandManager`, hour actions).
- `CommandExportManager.makeSelectedExportable` (`CommandExportManager.java:270-287`) — registered line 114.
- `ReplayableCommand_makeExportable.java` + `ReplayableCommand.makeExportable()`
  (`ReplayableCommand.java:413-430`) — registered line 103.

So the *removal* of strand 6 was NOT applied. This is **DIVERGENCE (missed removal)** relative to the
authoritative maint HEAD, which deleted all of it.

Behavioural impact assessment: LOW / cosmetic-dead-weight, NOT a functional regression.
- The *new* `CommandManager` model (the live export path) does not use `makeExportable` or
  `makeSelectedExportable` at all; it drives export via `isKnownParticipants` filtering. The legacy
  `CommandExportManager.makeSelectedExportable` only toggles `ReplayState.EXPORTED → UNDEFINED` on the old
  `getExported` collection.
- Impact is that main exposes TWO parallel manager UIs (legacy `CommandExportManager` with its
  EXPORTED/makeExportable lifecycle, plus the new `CommandManager`), whereas maint HEAD exposes only
  `CommandManager`. This is extra/stale surface area, not missing behaviour.
- Related side-effect: main's `getRecordedOrReplayed` collection query
  `findForegroundSinceTimestampAndWithReplayRecordedOrReplayed` includes `ReplayState.EXPORTED`
  (UNDEFINED, EXPORTED, OK) — retaining the EXPORTED lifecycle the task flags as "removed"; maint HEAD's
  `findForegroundSinceTimestampAndWithReplayUndefinedOrOk` uses only (UNDEFINED, OK). Consistent with the
  legacy retention.

Verdict: **DIVERGENCE — removal NOT applied.** Classification: **stale legacy retained (superset), not a
functional gap.** If parity with maint HEAD is the goal, main should delete `CommandExportManager`,
`ReplayableCommand_makeExportable`, `makeSelectedExportable`, deregister them, and drop `EXPORTED` from the
`RecordedOrReplayed` query. Flagged as MISSED-REMOVAL (low behavioural risk) rather than intentional, since
there is no positive evidence in main (test/comment) that dual models are deliberate.
