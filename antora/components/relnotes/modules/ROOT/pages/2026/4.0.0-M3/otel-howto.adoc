This guide starts with Boot-managed tracing and metrics, then changes tracing ownership to the OpenTelemetry Java agent.
Both modes send traces to Jaeger and Micrometer metrics to Prometheus, with Grafana for exploration.
Only one SDK/export pipeline owns tracing in each run.
Start with the default configuration to see request, interaction and persistence spans, then try duration filtering in the duration-filtering example below.

== Start the local telemetry services

From the Causeway repository root, with Docker Desktop or a Docker daemon running and Docker Compose v2 or later available:

[source,bash]
----
./scripts/jaeger-local.sh start
./scripts/metrics-local.sh start
----

The first command starts Jaeger; the second starts Prometheus and Grafana and provisions Grafana's Prometheus data source.
Each script checks readiness independently.
The Petclinic launcher does not start or stop these services.
Repeated starts reuse running services.
All published ports bind to localhost.

[cols="1,2",options="header"]
|===
|Address |Purpose
|http://localhost:16686 |Jaeger trace UI
|http://localhost:4318/v1/traces |Jaeger OTLP HTTP trace receiver
|http://localhost:9090 |Prometheus query UI
|http://localhost:9090/api/v1/otlp/v1/metrics |Prometheus OTLP HTTP metrics receiver
|http://localhost:3000 |Grafana; initial login `admin` / `admin`
|===

Jaeger stores traces in memory; Prometheus and Grafana data directories use size-limited tmpfs.
There are no persistent data volumes or host data directories.
Stopping or restarting the containers discards their runtime data, including Grafana password changes and dashboards created in the UI.
Read-only configuration files remain in the repository.

== Run with Boot-managed telemetry

Use a checkout whose Causeway dependencies have been built and installed into your local Maven repository.
The launcher builds the webcomponents modules; changes to other modules (such as the Wicket viewer) must be installed before running it.
The Petclinic launcher requires Maven and a supported build JDK, respects `JAVA_HOME` and `MVN`, and runs in the foreground:

[source,bash]
----
./viewers/webcomponents/sample-htmx-petclinic/run-with-telemetry.sh
----

[TIP]
====
Additional Maven options can be specified after `--`, for example `run-with-telemetry.sh -- -o` for an offline build.
====

The launcher activates the Maven `observation` profile for dependencies and the Spring `observation` profile for framework instrumentation and export configuration.
Boot owns tracing; Micrometer exports metrics.
Traces are fully sampled and metrics are exported every ten seconds.
No Java agent is attached in this mode.
Nonempty username and tenancy attributes are always included.
Duration filtering is disabled by default, so even short successful JPA spans are retained.
Remove external `causeway.observation.*` overrides when checking these defaults.

=== Equivalent configuration for another application

If you are following along with Petclinic, the launcher already supplies this configuration; continue to <<inspect-traces-and-metrics>>.

Use the BOM-managed starter, which includes the Micrometer OTLP metrics registry:

[source,xml]
.pom.xml
----
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-opentelemetry</artifactId>
</dependency>
----

Activate `observation` alongside the application's other Spring profiles:

[source,yaml]
.application.yaml
----
spring:
  application:
    name: my-causeway-app
  profiles:
    active: observation
management:
  tracing:
    sampling:
      probability: 1.0
  opentelemetry:
    tracing:
      export:
        otlp:
          endpoint: http://localhost:4318/v1/traces
  otlp:
    metrics:
      export:
        enabled: true
        url: http://localhost:9090/api/v1/otlp/v1/metrics
        step: 10s
        aggregation-temporality: cumulative
----

The two export endpoints are deliberately different.
Sending metrics to Jaeger's `/v1/metrics` produces HTTP 404 errors even if trace export works.
No custom `OtlpConfig` bean is needed.
Full sampling and frequent metrics export are useful for this local verification setup.

=== Inspect traces and metrics

In Jaeger:

* select service *Causeway Pet Clinic*
* click *Find Traces*
* open a recent trace from a domain operation.
+
HTMX domain operations use `/graphql`; Wicket requests use `/wicket/` paths.

* Select the enclosing HTTP server span to see `causeway.execution.mode=foreground`; this includes static asset requests as well as domain operations.

* Expand the span tree and inspect the spans
+
Span display names are contextual, for example `Action <member>` or `Persist <entity type>`.

* select the *Causeway Root Interaction* span, and inspect its *Attributes*, such as:

** `causeway.interaction.language`
** `causeway.interaction.timezone`
** `causeway.user.impersonating`

+
`causeway.user.name` contains the authenticated username, not the pet owner being edited.
`causeway.user.multiTenancyToken` is included when the user has a nonempty tenancy token; the sample bypass user normally has none.

* These user attributes are always included when nonempty on interaction spans; they are not added to the enclosing HTTP server span.
* The root interaction also has `causeway.interaction.id`, the UUID used by Causeway's interaction/command, in both tracing modes.
+
This is distinct from Jaeger's trace ID and span ID, and is not copied onto the HTTP span or nested interactions.
* Note that static asset requests, such as `pdf.worker.min.mjs`, may contain only HTTP/security spans and therefore have no interaction UUID.



=== Micrometer

Underlying Micrometer operation names are categories such as `causeway.member.action` and `causeway.jpa.persist`.

Repeat operations on different owners:

* the Causeway member/JPA span names and member/entity metadata describe the operation and type

Note that instance identifiers, object titles or argument values and _not_ included in the spans.

HTTP instrumentation can still record request paths containing object identifiers; interaction identity attributes are recorded separately.

Open Prometheus directly or log in to Grafana (`admin` / `admin`).

In Grafana:

* choose *Explore*
* select *Prometheus* in the data-source dropdown at the top, and switch to *Code* mode for PromQL.

The built-in *Grafana* data source and its *Random Walk* query show generated sample data, not Petclinic metrics.

* The provisioned *Prometheus* source is also listed under *Connections → Data sources*.

After exercising Petclinic, wait 10–20 seconds and try these queries separately:

* JVM memory used bytes
+
[source,promql]
----
jvm_memory_used_bytes
----

* discover available Causeway metric names and counts their series:
+
[source,promql]
----
count by (__name__) ({__name__=~"causeway_.*"})
----

* select an actual metric name to inspect values.

Note that Prometheus metric names can differ from contextual span names, including dots translated to underscores.

The username and tenancy attributes are high-cardinality span metadata; they are not added as Micrometer metric labels.

* Grafana queries the internal Docker address `http://prometheus:9090`; Petclinic sends to `localhost:9090` from the host.


=== Find requests and correlate interactions

In Jaeger, select *All Span Names* and use the *Attributes* field for these searches separately:

[source,text]
----
causeway.execution.mode=foreground
----

Copy the `causeway.interaction.id` from a root interaction, then replace the example UUID below with that value:

[source,text]
----
causeway.interaction.id=12345678-1234-1234-1234-123456789abc
----

The execution mode is on the entry span and the UUID is on the root interaction span.
Do not combine these into a same-span attribute query: no single span is required to carry both.
The UUID can correlate command replay with the originating command; replay retains that command's effective identifier even if it replaces an ID allocated when the interaction opened.
Sampling, export failures, time ranges and Jaeger's in-memory retention can limit matches; restarting Jaeger loses earlier traces.
Neither attribute adds an interaction UUID or execution-mode label to Causeway's Micrometer meters.


=== Enable duration filtering

The JPA duration threshold defaults to `0ms`, which disables filtering.
To filter short successful JPA spans, stop Petclinic with Ctrl-C, leave the telemetry services running, and set a positive threshold for the next Boot-managed run:

[source,bash]
----
export CAUSEWAY_OBSERVATION_JPA_DURATION_THRESHOLD=1s
./viewers/webcomponents/sample-htmx-petclinic/run-with-telemetry.sh
----

This environment variable binds `causeway.observation.jpa-duration-threshold`.
The example uses one second to make the filtering effect easy to see; choose a smaller threshold such as `2ms` for less aggressive filtering.
Repeat a database-backed action and compare a new trace with one from the unfiltered run.
Existing traces are unchanged.
In Jaeger, look for contextual names such as *Fetch by Bookmark* and *Refresh*, followed by the entity type; these correspond to `causeway.jpa.fetch-by-bookmark` and `causeway.jpa.refresh`.
Short successful spans with these names below the threshold should disappear when filtering is enabled, while *Transaction*, *Transaction Creation*, *Transaction Completion* and *Action* remain because they are outside the JPA duration filter.

Duration filtering is a span export policy, not a guarantee about metric suppression.
It can leave exported children whose JPA parent was discarded.
To check context cleanup, trigger an exception during observed work, then a successful action in the same run; a rejected UI validation alone need not produce an error span.

To return to the defaults, stop Petclinic and unset the overrides before restarting:

[source,bash]
----
unset CAUSEWAY_OBSERVATION_JPA_DURATION_THRESHOLD
----

== Switch to agent-managed tracing

Stop the Boot-managed Petclinic process, keep all three telemetry services running, then add `--agent`:

[source,bash]
----
./viewers/webcomponents/sample-htmx-petclinic/run-with-telemetry.sh --agent
----

The same Jaeger and Prometheus/Grafana UIs remain available.
User attributes are included in both modes; inspect new traces after exercising the app again.
The agent now owns the tracing SDK, exporter and automatic HTTP/JDBC instrumentation.
An explicit registry bridge joins Causeway observations to that context, and the `agent` profile disables competing Boot tracing auto-configuration.
Micrometer continues to export metrics to Prometheus in both modes; the agent's own metrics exporter is disabled to avoid duplicate JVM metrics.
This setup also disables agent log export.

On first use, Maven obtains agent 2.31.1 (matching the compatibility fixture) into the sample's `target/agents/` directory.
The launcher attaches it to the application JVM with `spring-boot.run.agents`, not to Maven itself.
Use an existing JAR if preferred:

[source,bash]
----
OTEL_JAVAAGENT_PATH=/absolute/path/to/opentelemetry-javaagent.jar \
  ./viewers/webcomponents/sample-htmx-petclinic/run-with-telemetry.sh --agent
----

The launcher sets OTLP HTTP trace export, full trace sampling and service name *Causeway Pet Clinic* by default.
`OTEL_SERVICE_NAME` and `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` can override the agent's trace service name and destination.
Micrometer's destination remains the separately configured metrics URL.

The launcher disables duration filtering in agent mode: the agent exporter does not consume Spring's discard predicate.
Use Boot mode to enable duration filtering.
Inspect a database-backed operation in Jaeger: framework spans should join automatic HTTP/JDBC context without duplicate framework export.
The launcher reserves profile, agent and application-argument settings so conflicting Maven options cannot silently replace this wiring.

=== Apply the same change to another application

Keep the metrics configuration above, add the BOM-managed `io.micrometer:micrometer-tracing-bridge-otel` dependency, and register the following configuration through component scanning or an explicit import:

[source,java]
----
import java.util.List;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Profile;

import io.micrometer.observation.ObservationRegistry;
import io.micrometer.tracing.handler.DefaultTracingObservationHandler;
import io.micrometer.tracing.otel.bridge.OtelBaggageManager;
import io.micrometer.tracing.otel.bridge.OtelCurrentTraceContext;
import io.micrometer.tracing.otel.bridge.OtelTracer;
import io.opentelemetry.api.GlobalOpenTelemetry;

/** Bridges Causeway observations into the agent's HTTP/JDBC trace context. */
@Configuration(proxyBeanMethods = false)
@Profile("agent")
public class AgentObservationConfiguration {
    @Bean
    io.micrometer.tracing.Tracer agentTracer() {
        // The attached agent owns the global SDK and exporter. Do not construct another SDK here.
        var currentContext = new OtelCurrentTraceContext();
        return new OtelTracer(GlobalOpenTelemetry.getTracer("org.apache.causeway"), currentContext,
                event -> {}, new OtelBaggageManager(currentContext, List.of(), List.of()));
    }

    @Bean
    ObservationRegistry agentObservationRegistry(io.micrometer.tracing.Tracer tracer) {
        var registry = ObservationRegistry.create();
        registry.observationConfig().observationHandler(new DefaultTracingObservationHandler(tracer));
        return registry;
    }
}
----

The registry and entry-span classifier share this tracer bean, which uses the agent's global OpenTelemetry instance without constructing another SDK.
A custom registry without a tracer bean can still create observations, but cannot classify agent-owned entry spans.
When observations are active, supply a single tracer or designate a primary if multiple tracers exist.
Add an agent-specific configuration that replaces tracing ownership while retaining Micrometer metrics:

[source,yaml]
.application-agent.yaml
----
spring:
  autoconfigure:
    exclude:
      - org.springframework.boot.opentelemetry.autoconfigure.OpenTelemetrySdkAutoConfiguration
      - org.springframework.boot.micrometer.tracing.opentelemetry.autoconfigure.OpenTelemetryTracingAutoConfiguration
      - org.springframework.boot.micrometer.tracing.opentelemetry.autoconfigure.otlp.OtlpTracingAutoConfiguration
      - org.springframework.boot.micrometer.tracing.autoconfigure.MicrometerTracingAutoConfiguration
      - org.springframework.boot.webmvc.autoconfigure.WebMvcObservationAutoConfiguration
management:
  opentelemetry:
    map-environment-variables: false
  tracing:
    export:
      enabled: false
causeway:
  observation:
    jpa-duration-threshold: 0ms
----

The exclusions above match the Spring Boot 4.2.0-M1 baseline used by this checkout.
The WebMVC exclusion lets the agent own the HTTP entry span without a second Boot HTTP observation around it; foreground classification then tags the agent's span.
It also removes Boot's HTTP request observation meters in this configuration; JVM and Causeway Micrometer metrics remain available.
Build the application with the bridge configuration included.
Activate `observation,agent` alongside any other required application profiles and attach the agent to the application JVM:

[source,bash]
----
export OTEL_SERVICE_NAME=my-causeway-app
export OTEL_TRACES_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf
export OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://localhost:4318/v1/traces
export OTEL_TRACES_SAMPLER=always_on
export OTEL_METRICS_EXPORTER=none
export OTEL_LOGS_EXPORTER=none
java -javaagent:/absolute/path/to/opentelemetry-javaagent.jar \
  -jar application.jar --spring.profiles.active=observation,agent
----

`OTEL_METRICS_EXPORTER=none` disables the agent's exporter.
`management.opentelemetry.map-environment-variables=false` prevents Boot from mapping that agent flag onto Micrometer and disabling its metrics too.
The shared `management.otlp.metrics.export.enabled=true` configuration therefore retains Micrometer's separate metrics pipeline.
When returning to Boot-managed tracing, remove `-javaagent`, deactivate the `agent` profile, and unset the exported `OTEL_*` variables above so that Boot does not inherit the agent-only settings.

== Inspect and stop the local services

[source,bash]
----
./scripts/jaeger-local.sh status
./scripts/metrics-local.sh status
./scripts/jaeger-local.sh logs
./scripts/metrics-local.sh logs
----

When finished, stop Petclinic with Ctrl-C, then stop all telemetry services:

[source,bash]
----
./scripts/jaeger-local.sh stop
./scripts/metrics-local.sh stop
----

The Jaeger command discards stored traces.
The metrics command discards metrics and Grafana UI changes and removes its Compose network.
Each script manages only its own services.
`./scripts/metrics-local.sh config` validates Compose configuration without starting services.
