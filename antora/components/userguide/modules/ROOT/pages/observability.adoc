Causeway's `observation` Spring profile enables framework observations for interactions, actions, property editing, transactions, execution publishing, metamodel initialization and JPA operations.
Without that profile, Causeway uses a no-op integration; an application's own observation registry remains usable.

== Boot-managed tracing

Use the main BOM's `spring-boot-starter-opentelemetry` and activate the profile:

[source,yaml]
----
spring:
  profiles:
    active: observation
management:
  opentelemetry:
    tracing:
      export:
        otlp:
          endpoint: http://localhost:4318/v1/traces
----

Boot owns tracing configuration and export in this configuration.
Causeway uses a supplied single or primary `ObservationRegistry`, with a fallback when none is supplied.
Multiple registry candidates without a primary produce a configuration error.
An active observation profile does not require an agent or exporter to start successfully.

== Java-agent-owned tracing

An alternative configuration lets the OpenTelemetry Java agent own the SDK, automatic HTTP/JDBC instrumentation and export.
Add the BOM-managed `io.micrometer:micrometer-tracing-bridge-otel` dependency and activate `observation,agent`.
Causeway supplies the missing tracer and registry beans, bridges observations to the agent's global context, and automatically excludes competing Boot SDK/tracing and WebMVC observation configuration.
No application Java bridge or manual exclusions are needed.

A supplied registry or tracer takes precedence over the corresponding default.
A custom registry remains responsible for its handlers; those handlers and Causeway's entry-span classifier must share a single or primary tracer.
Causeway does not construct an SDK or exporter, and the profiles do not attach an agent: attachment is still required for agent export.

Launch the JVM with `-javaagent:/path/to/opentelemetry-javaagent.jar` and configure the agent's service name, sampler and OTLP endpoint through its normal settings.
For example, a local tracing-only run can use:

[source,bash]
----
export OTEL_SERVICE_NAME=my-causeway-app
export OTEL_TRACES_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://localhost:4318/v1/traces
export OTEL_METRICS_EXPORTER=none
export OTEL_LOGS_EXPORTER=none
java -javaagent:/path/to/opentelemetry-javaagent.jar -jar application.jar --spring.profiles.active=observation,agent
----

The registry and entry-span classifier share the exposed Micrometer tracer.
The WebMVC exclusion avoids a second Boot HTTP observation inside the agent's entry span; Boot HTTP request observation meters are consequently absent, while other Micrometer metrics remain available.
Causeway disables Boot environment-variable mapping for the `agent` profile, preventing the agent's `OTEL_METRICS_EXPORTER=none` from disabling a separately configured Micrometer metrics exporter.
Do not also construct an independent SDK/export pipeline in this configuration.
The agent configuration is an explicit application choice; it does not replace the Boot-managed default.
With the agent profile but without the `observation` profile, automatic agent spans remain active and Causeway observations remain inactive.

== Execution classification and interaction correlation

With the `observation` profile active, two attributes help you find relevant traces:

* `causeway.execution.mode` identifies the entry span as `foreground` for HTTP requests (including static resources), or `background` for `RunBackgroundCommandsJob` executions.
Background classification requires an existing job span, supplied by instrumentation such as the Java agent's Quartz support.
* `causeway.interaction.id` appears on *Causeway Root Interaction* and contains the interaction's UUID.
It is distinct from the trace ID and retains the command's identifier during replay, allowing you to find related executions.

User identity attributes are included automatically alongside interaction correlation; they are not added as metric labels.
In Jaeger, select *All Span Names* and search separately by execution mode or interaction ID: they appear on different spans.
Searches can only find traces that were sampled, exported and retained by the backend.

== JPA span retention

Causeway retains JPA observations regardless of duration in both Boot-managed and agent-managed tracing.
The former `causeway.observation.jpa-duration-threshold` property has been removed; remove it and its environment override from existing configurations.
Filtering a JPA parent independently could leave its JDBC children without an exported parent.
Normal sampling, exporter failures and application-defined policies still determine which spans reach the backend.

== Semantic member spans

Action observations use the fixed Micrometer operation `causeway.member.action` and contextual name `act <logical-type>#<member>`.
For mixed-in actions, the name identifies the contributed domain action rather than the mixin's implementation method.
Mixed-in property and collection accesses use `causeway.property.access` / `causeway.collection.access`, with contextual prefixes `prop` / `coll`.
Regular property updates remain `causeway.member.property-update` observations.

Inspect `causeway.action.id`, `causeway.property.id` or `causeway.collection.id` for the complete canonical domain identifier.
Action identifiers retain declared parameter signatures.
The existing generic `causeway.member.id` retains the physical invoked member's metadata; use the category-specific keys for domain-facing searches.

Contextual names retain casing and use a 50-character display budget.
Names that exceed the budget first use a namespace-free type name, then truncate if still necessary; complete identifier attributes remain unchanged.
Names contain static model identifiers, not instance titles, bookmarks or argument values.
Unresolved mixed-in association metadata falls back to an action observation.

Both Boot and agent modes use this naming without extra settings.
The root interaction remains a separate span; semantic HTTP entry names describe the request outcome as explained below.

== Semantic foreground trace names

With observations active, Causeway names the existing HTTP entry span from the highest-priority supported outcome: `act <logical-type>#<action>`, `prompt <logical-type>#<action>` or `view <logical-type>`.
Actions outrank prompts, prompts outrank views and the first candidate wins equal-priority ties.
A real action nominates only when its domain-facing identity matches the interaction command; calculated association access, pass-through work and unmatched nested/helper actions do not become the request outcome.
Wicket full object-page rendering nominates a view, and enclosing action-prompt rendering nominates a prompt.
Arbitrary Ajax subregions do not invent page-view outcomes.
Requests with no supported candidate retain the tracing owner's supplied name.

The selected entry display follows the same case-preserving 50-character compaction as member spans and is also available in `causeway.trace.name`.
Entry attributes retain the full `causeway.action.id` (including declared parameter signatures) for actions/prompts or `causeway.object.type` for views.
No instance titles, bookmarks or argument values are included.
Existing HTTP attributes, execution mode, trace/span identity and child parentage remain intact; identity and correlation attributes remain on their existing interaction spans.
Use HTTP method and route/path attributes for route-based grouping, since an entry's display now identifies domain work when a candidate exists.

Both Boot-managed and agent-managed tracing use the existing integration without another flag or application code.
Wicket entry nominations remain effective with `NONE` detail and exhausted request budgets, independently of region span admission.
Nomination state belongs to synchronous work in the initial servlet dispatch; it is cleared on success/failure and is not propagated across threads or redispatches.

In the M3 Petclinic how-to, open an owner in Wicket, open Update Name, then submit it and inspect separate fresh traces in Jaeger.
Expected entry displays are `view petclinic.PetOwner`, `prompt petclinic.PetOwner#updateName` and `act petclinic.PetOwner#updateName`.
Select the HTTP entry for the outcome attributes and the child regions/member spans for their own rendering/execution detail.
GraphQL/HTMX can nominate matching top-level actions but does not supply Wicket view/prompt nominations.

== Wicket preparation and rendering regions

With observations active, Wicket domain-object pages emit `causeway.wicket.page.prepare` (`prepare <logical-type>`) around initial page construction and configuration/descendant preparation, and `causeway.wicket.page.render` (`render <logical-type>`) around markup rendering.
Preparation closes before markup rendering begins.
Visible fieldsets, regular object properties, parented collections and object action controls use `causeway.wicket.fieldset.render`, `causeway.wicket.property.render`, `causeway.wicket.collection.render` and `causeway.wicket.action.render`.
Their displays use `render fieldset <id>`, `render property <logical-type>#<member>`, `render collection <logical-type>#<member>` and `render action <logical-type>#<member>`.
Action prompts use `causeway.wicket.action.prompt.render`, displayed as `prompt <logical-type>#<action>`.

These UI boundaries enclose actual rendering; domain invocation/access spans remain separate observations.
Each region carries the full static `causeway.object.type` and its applicable `causeway.fieldset.id`, `causeway.property.id`, `causeway.collection.id` or `causeway.action.id`.
Action controls and prompts identify contributed domain actions, retaining declared parameter signatures in attributes.
Displays follow the same case-preserving 50-character compaction policy as member spans; instance identifiers, titles and argument values are omitted.

A full page has nested page/member rendering regions.
An Ajax subtree update retains its request/interaction ancestry and can render a property or collection without rendering the page.
Hidden components, action parameter widgets and decorative table widgets do not acquire these member-level regions.
Logical property cells and eligible row actions in parented collections do.
Outstanding scopes are unwound at request completion or on error before interaction/request parents close, and active telemetry is excluded from serialized page state.

Use the existing Petclinic setup in the M3 how-to: open an owner, inspect its visits collection and open Update Name to see preparation, collection rendering and prompt regions.
These observations work with either existing tracing owner without another flag.
Parented collections use `causeway.wicket.collection.prepare`, `causeway.wicket.collection.row.prepare`, `causeway.wicket.collection.table.render`, `causeway.wicket.collection.table.header.render`, `causeway.wicket.collection.table.body.render`, `causeway.wicket.collection.table.footer.render` and `causeway.wicket.collection.row.render`.
Row preparation measures actual population; row rendering belongs under the table body.
Only participating paginated rows are measured, without extra loading or counting.
Rows carry their static collection identifier and element type, never an instance identifier or row index.
Standalone result and action-parameter tables are excluded.

=== Wicket detail and request budgets

`causeway.viewer.wicket.observation.detail` defaults to `MEMBERS`.
The cumulative levels are `NONE` (no Causeway semantic Wicket observations), `PAGE` (page preparation/rendering and prompts), `REGIONS` (also fieldsets, collections and table phases), `ROWS` (also rows) and `MEMBERS` (also logical properties and eligible actions).
`causeway.viewer.wicket.observation.max-spans-per-request` defaults to `0`, meaning unlimited; a positive value bounds cumulative Wicket observation starts across one request, with no refund on closure.
Negative values and invalid detail fail startup.
A finite budget reserves ten percent, rounded up and capped at sixteen places, for structural page/region observations.
The absolute limit still applies, so structural observations can also be omitted.

Set `CAUSEWAY_VIEWER_WICKET_OBSERVATION_DETAIL=REGIONS` and `CAUSEWAY_VIEWER_WICKET_OBSERVATION_MAX_SPANS_PER_REQUEST=100` before starting the existing Petclinic telemetry launcher to inspect a bounded collection trace.
These settings work with either tracing owner and take effect at startup.
They affect only Causeway semantic Wicket observations: The enclosing Apache Wicket Request Cycle, HTTP, interaction, transaction, domain, JPA and agent JDBC spans retain their existing behavior.
Omitted boundaries open no scope; underlying work still executes and emitted descendants join the current surviving ancestry.

Admitted collection preparation/render spans report numeric callback summaries: `causeway.wicket.collection.row.count`, `causeway.wicket.collection.row.duration.total.nanos` and `causeway.wicket.collection.row.duration.max.nanos`.
Render spans also report `causeway.wicket.collection.logical-cell.count` and positive `causeway.wicket.collection.suppressed.children`.
Summaries include row/member work whose individual observations were omitted; they do not count off-page rows or total collection size.
Logical cells count property/action callbacks, not DOM cells or physical columns.
Positive `causeway.wicket.suppressed.detail` and `causeway.wicket.suppressed.budget` counts on surviving page/region spans explain rejection by detail or budget.
No synthetic summary carrier is created when all potential carriers are omitted.

These rendering observations apply to Wicket; page/prompt nomination is also Wicket-specific. Other viewers retain their existing domain observations and can nominate eligible top-level actions.

== Observation names and metadata migration (CAUSEWAY-4096)

Micrometer's operation name identifies an operation category and its meters.
The contextual name is a separate, human-readable label used by the tracing handler for exported span names.
For example, `causeway.jpa.persist` is the operation name and `Persist com.example.Customer` is its contextual/exported name.
Static entity type, member identifier and declared query name can appear in contextual names and the attributes `causeway.entity.type`, `causeway.member.id` and `causeway.query.name`.
Bookmarks, instance identifiers, titles, query descriptions and query arguments are excluded from these Causeway-generated fields.

[cols="2,2,2",options="header"]
|===
|Previous observation name |Operation name |Contextual/exported name
|`Fetch by Bookmark (...)` |`causeway.jpa.fetch-by-bookmark` |`Fetch by Bookmark <entity type>`
|`Fetch all Instances (...)` (all instances) |`causeway.jpa.fetch-all` |`Fetch all Instances <entity type>`
|`Fetch all Instances (...)` (named query) |`causeway.jpa.named-query` |`Named Query <entity type> <query name>`
|`Persist (type=...)` |`causeway.jpa.persist` |`Persist <entity type>`
|`Refresh (type=...)` |`causeway.jpa.refresh` |`Refresh <entity type>`
|`Remove (type=...)` |`causeway.jpa.remove` |`Remove <entity type>`
|`Detach (type=...)` |`causeway.jpa.detach` |`Detach <entity type>`
|`Action Invocation (...)` |`causeway.member.action` |`act <domain logical type>#<member>`
|`Property Update (...)` |`causeway.member.property-update` |`Property Update <member identifier>`
|`Execution Publishing (subscribers=N)` |`causeway.execution.publish` |`Execution Publishing`
|===

Update meter queries using the operation names and trace searches using contextual names or attributes.
Legacy observations are not emitted alongside the replacements.
Other existing fixed operation names are unchanged.
Missing static member identifiers are omitted; runtime object data is never a fallback.
Publishing counts are emitted as `causeway.execution.subscriber-count` high-cardinality data rather than a meter dimension or part of a name.

Causeway always includes nonempty `causeway.user.name` and `causeway.user.multiTenancyToken` on interaction spans.
They describe the interaction's authenticated user and tenancy, and are high-cardinality span attributes rather than metric labels.
Empty values are omitted; impersonation status and locale metadata remain available.

== Validated baseline and regression fixture

The foundation fixture validates Boot 4.2.0-M1, Micrometer Observation 1.18.0-M1, Micrometer Tracing 1.8.0-M1, OpenTelemetry API/SDK 1.64.0, agent 2.31.1, Java 25.0.4 and Maven 3.9.13.
These are the tested versions, not a requirement to override the application's Causeway BOM.

The child-process fixture uses production interaction and action services and the JPA facet with mocked non-telemetry collaborators, a local JDK HTTP server, H2, and a local OTLP receiver.
Its JPA backend is controlled; agent mode instruments real H2 JDBC automatically, while Boot mode explicitly wraps the SQL call in a fixture observation.
It proves agent HTTP/framework/JPA/JDBC ancestry, one framework span per invocation, a failure followed by a successful request on the same worker, Boot-managed export, duration-independent JPA retention, inactive-profile behavior and operation without an agent/exporter.
The additional entry-point fixture uses real Tomcat servlet and Quartz instrumentation with controlled business collaborators, verifying fixed-key classification and effective replay UUIDs in both trace ownership modes.
The Wicket fixture additionally runs real component lifecycle and Ajax callbacks with production region helpers and request observation/cleanup handlers, verifying full-page versus subtree ancestry, failure followed by success, identity and inactive/missing-exporter behavior in both modes.
Its JDK HTTP server uses Boot’s standard receiver handler bound to the real request in Boot mode and automatic HTTP instrumentation in agent mode.
The semantic entry fixture additionally uses real servlet filters, runtime action eligibility and Wicket render callbacks to verify final exported action/prompt/view names, priority, unchanged HTTP metadata/ancestry, suppressed-region naming and failure followed by un-nominated requests on one worker under both tracing owners.
Its domain/model collaborators are controlled; it does not replace interactive Petclinic verification or prove every servlet container/viewer integration or a full persisted-command replay.

From the repository root, after building the required main artifacts:

[source,bash]
----
mvn -f regressiontests/tracing-compatibility/pom.xml test
----

Fixture output is retained under `regressiontests/tracing-compatibility/target/fixture-*.log`.
The fixture drains output while the child runs and enforces a two-minute process timeout.
